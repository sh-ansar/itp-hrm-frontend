# Роли: вход, ввод данных, результат и ограничения

Текущая серверная политика, без расширения прав только на frontend. Маршруты HRM используют `/hrm-api`; настоящие записи не хранятся в localStorage.

| Пользователь | После входа / отображение | Что вводит | Что получает | Что запрещено |
|---|---|---|---|---|
| Администратор компании | Полный разрешённый HR-интерфейс, роли и права | Кадровые данные, графики, календарь, назначение HR/руководителя/сотрудника и подразделений | Сохранённые записи, версии, журнал назначений; рабочие/выходные/праздничные даты | Выдача роли администратора и изменение защищённых администраторов через обычный API |
| HR-специалист | Реестр, карточки, штатка, кадровые процессы, документы, отчёты, графики и отпуска | Кадровые данные, договоры, кадровые операции, табель, заявки/премии в пределах реализованного workflow | Полные разрешённые HR-поля и состояние сохранения; закрытые разделы через private profile/records | Управление ролями, изменение общего календаря, самостоятельное согласование там, где нужен другой согласующий |
| Руководитель подразделения | Разрешённые реестр, оргструктура, время и отпуска | Личные настройки; административные формы отсутствуют | Только сотрудники явно назначенных подразделений и разрешённые данные | Чужие подразделения/компании, кадровые записи, договоры, банковские/документные сведения, роли, календарь |
| Обычный сотрудник | Личные настройки, без административного sidebar и поиска сотрудников | Язык/тема устройства, личные уведомления, собственный пароль | Свои настройки и сохранение уведомлений на сервере | Реестр и управление сотрудниками, роли, кадровые документы других людей и административные операции |

## Вход и выход

- После входа выбирается разрешённая стартовая страница. Для сотрудника это настройки, а не сообщение об ошибке доступа.
- Прямой переход в запрещённый раздел показывает ограничение доступа; сервер отдельно отклоняет запрос.
- Выход завершает сессию и очищает кеш разрешений; повторный вход получает права текущего пользователя.
- Роли и department scopes являются серверными данными. После изменения роли и reload интерфейс строится заново по `/me/access`.

## Календарь

Администратор выбирает диапазон внутри месяца, тип дней, минуты и описание. «Применить к периоду» изменяет только черновик; сохранение отправляет один batch PUT с исходными revision для каждой изменённой даты. Не затронутые даты не перезаписываются. При конфликте возвращается ошибка и требуется обновление данных.

## Проверка

`calendar-bulk.test.mjs`: мобильный drawer, три ранее заполненные даты, один PUT, reload, revision 2, сохранение соседней даты и запрет диапазона вне месяца.

`role-user-flows.test.mjs`: четыре настоящих synthetic login, разная навигация и состав API, серверные запреты, чужая компания/подразделение, выдача роли руководителя через UI и проверка нового scope после reload.

## Оставшееся ограничение

У учётной записи пока нет надёжной связи с кадровой записью сотрудника. Поэтому личная карточка, собственный табель и самостоятельные заявки сотрудника не выдаются через догадки по имени/email. Для полноценного employee self-service нужна явная, проверяемая company-scoped связь user ↔ employee и отдельные авторизованные endpoints.
