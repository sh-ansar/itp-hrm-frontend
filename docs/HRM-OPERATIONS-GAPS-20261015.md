# HRM — фактические пробелы и порядок закрытия (15.10.2026)

Документ для следующего разработчика. Стек: Laravel 12 + Vue 3 + PostgreSQL. Источником истины являются серверные модели и API, а не данные demo-режима.

## 1. Что есть на текущем main

| Область | Реализация | Ограничение |
|---|---|---|
| Приём, перевод, увольнение | Laravel `PersonnelActionController`, `personnel_actions`, история назначений; Vue `PersonnelActionForm` | Только `hire / transfer / termination`. События о выплатах или социальных отпусках этим типом не представлены |
| Отпуска и согласование | `LeavePlanWorkflow`, `leave_requests`: draft → submitted → approved / rejected, отмена черновиков и заявок; однократная публикация в `employee_leaves` | Только HR/администратор создают заявки, решение — company_admin. Не полный пользовательский кабинет, нет многоступенчатой маршрутизации, делегирования, начисления остатков и возврата из уже утверждённого отпуска |
| Календарь рабочего времени | `ProductionCalendarWriter` и редактор; `workday / shortened / weekend / holiday`, ревизии, аудит | По данным компании, без автоматического определения праздников. Запись включается отдельным feature flag; правка разрешена администратору |
| Справочники | Должности: отдельный CRUD API. Типы отпусков: API в панели отпусков | Общая страница `DirectoryHubView` содержит справочные примеры в памяти, не полноценные записи PostgreSQL; добавление там доступно только в demo-режиме |
| Реестр и карточка | Реальные Laravel-контракты, кадровые и приватные поля, документы, образование | Расчёты, начисления, табель и часть полей зависят от будущих доменных модулей |
| Роли | Проекция разрешений из Laravel, `company_admin / hr_specialist / department_manager / employee` | `roles.interface` отключена в реальном режиме; отсутствует готовый self-service обычного сотрудника |
| Сводные отчёты | Есть интерфейсы | Для части метрик нет подтверждённого backend-контракта; не подменять нулевыми/моковыми величинами |

## 2. Кадровые операции — следующие вертикальные срезы

1. **Премии и поощрения (P0).** Отдельная доменная сущность `employee_awards` или `compensation_events`, а не расширение `personnel_actions` фиктивным типом. Должны храниться вид начисления, валюта, сумма/процент и база расчёта, дата/период, основание, сотрудник, организация, статус, автор, согласующий и ссылки на документ/приказ. Раздельные полномочия инициатора и утверждающего; после утверждения — событие для бухгалтерской/зарплатной интеграции, **не** самостоятельное перечисление денег. Валидация, транзакция, аудит, отмена/сторно и запрет повторной проводки.
2. **Беременность и роды; отпуск по уходу за ребёнком (P0).** Отдельные виды защищённого отсутствия с основаниями, периодами, вложениями, сохранением рабочего места, продлением и досрочным возвращением. Пересечения с другими отпусками и табелем проверяются сервером. Правила расчёта и сроки зависят от юрисдикции и локального законодательства, их нельзя захардкодить под все компании. Не изменять трудоустройство как «увольнение».
3. **Больничный и иные подтверждаемые отсутствия (P1).** Заявка, документ, подтверждение, проверка пересечений и отражение в табеле.
4. **Командировки, отгулы, работа в выходной и сверхурочная работа (P1).** Согласование, даты/часы, компенсация, учёт и отмена.
5. **Изменение оклада/надбавок, дисциплинарные и иные действия (P1/P2).** Отдельные типизированные события, действующие с датой, формальное основание, история/аудит и контроль прав.

Не добавлять в выпадающий список доступных действий то, что не имеет работающей серверной операции. Для новых сущностей — Laravel migrations, DTO/FormRequest, Policy, service/workflow, controller, API resource, feature tests и Vue-панели с реальными контрактами.

## 3. Отпуска и согласование — что дополнить

- Внести `leave_balance_ledger` (начислено, использовано, перенесено, скорректировано, сторнировано) с уникальными ссылками на источник и версионированием; не рассчитывать остаток простым вычитанием количества заявок.
- Политики компании: календарные/рабочие дни, праздничные переносы, лимиты, перенос на следующий год, частичные дни, индивидуальные графики. Формальные настройки и версии политики обязательны.
- Универсальные `approval_instances / approval_steps`: инициатор → руководитель → HR → при необходимости финальное согласование; права и доступ на каждом шаге, делегирование, комментарии и таймлайн.
- Возможность самостоятельной подачи заявки сотрудником только после создания разрешённого self-service и связки `user ↔ employee`. Текущий HR workflow этого не заменяет.
- После утверждения: контролируемая публикация в `employee_leaves`, синхронизация с табелем, уведомления, печатные документы, отмена только через формальную процедуру.
- Контракты и миграции проектировать по компаниям (`company_id`), включая защиту от межклиентских ссылок и аудит персональных действий.

## 4. Производственный календарь

- **UI уже обновлён:** рабочие клетки — зелёные; выходные — красные; праздничные — жёлтые; неполные данные — пунктир. Одинаковая легенда для сетки и редактора, обе темы, мобильный/планшет/десктоп.
- Источник истины для боевой системы — сохранённый `day_type` в API компании. Нельзя автоматически считать субботу/воскресенье нерабочими или назначать праздники для сменного графика без выбранного расписания и политики.
- Кнопка «заполнить 5/2» в редакторе заполняет **только отсутствующие** даты; администратор проверяет праздники и переносы перед сохранением. Она не должна заменять официальные календари.
- В demo-данных есть **только явно помеченный пример** `2026-10-25` — День Республики. Он не переносится в production-базу и не служит автоматическим государственным календарём.
- Следующий этап: реестр официальных календарей по стране/региону/году, ручные изменения и опубликованные версии, импорт с проверкой переносов и организационных графиков.

## 5. Справочники

- Перекомпонован экран: слева дерево/навигация по категориям, справа просторная таблица с фильтрами; в мобильном виде горизонтальный список категорий, затем таблица с **локальным** горизонтальным скроллом.
- **Нет права объявить каталог готовым**: кроме должностей и отдельных типов отпусков здесь большинство записей всё ещё демонстрационные.
- Реализация следующего этапа: нормализованные таблицы `company_directory_entries` + специализированные таблицы правил тарификации/надбавок вместо универсального JSON для всех бизнес-правил; код, наименование, статус, сроки действия, версия, company_id, связь с сущностями. CRUD, фильтры, сортировка, ACL, аудит и импорт с валидацией.
- Не допускать «редактирования» справочника только в памяти браузера в режиме реального backend.

## 6. Критерии приёмки до объявления готовности

1. Feature-тесты Laravel: роли, запрет записи чужой компании, создание/решение/отмена, ревизии, повторное исполнение, пересечения дат, аудит.
2. Playwright с реальным PostgreSQL на изолированном тестовом контуре: администратор, HR, руководитель, сотрудник; запрет UI и прямых API; создание и повторное открытие записей после перезагрузки.
3. Календарь: проверка цветов **на PNG**, а не только `data-theme`, все три типа дня, `missing`, обе темы и ширины 375/768/1440.
4. Справочники: сравнение с ZIP `Item_Management`, без лишнего вертикального скролла у таблиц; адаптивность и различимый контраст в тёмной теме.
5. Отдельная PostgreSQL-база, независимый PHP runtime, резервное копирование и проверка восстановления, журнал операций и безопасное включение feature flags.

Прод-включение новых записывающих модулей — только после согласования правил заказчика и зелёных тестов, не по наличию кнопки во фронтенде.
